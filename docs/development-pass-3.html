The third development pass makes x3d.xray more useful by tightening the connection between a visual claim and the evidence supporting it. A repository glyph can be traced to a declared entity; a relation polyline can be checked against source membership and a bounded witness projection; some public witnesses can now be resolved to exact local Git objects. Time becomes an explicit query dimension, and scale becomes an experiment with retained inputs and disclosed measurement boundaries. These are foundations for an architecture instrument whose conclusions remain inspectable as its visual language grows.

The governing heuristic is to attach each assurance to the smallest claim it actually establishes. Exact source bytes, detector interpretation, source ownership, historical validity, static geometry, and rendered appearance require different evidence. Combining them into one reassuring badge would discard the distinction that makes the system valuable. The creative opportunity is to make those distinctions easy to explore: a source inspector beside a claim, a temporal counterexample beside a path, and a scale specimen beside its measurement receipt.

From a path string to an immutable witness

A public Git locator now identifies a canonical repository, a full immutable revision, an exact path, a blob, a span, and the detector identity and version. Verification reads the commit and walks its tree locally, rehashing commit, tree, and blob objects using the repository's SHA-1 or SHA-256 object format. It also checks SHA-256 digests over raw blob content and the selected span. Git object identities include Git's object header; raw-content and span digests describe different byte sequences and serve different purposes.

Line spans are one-based and inclusive; their byte boundaries are derived from LF-separated UTF-8 content. Byte spans are zero-based and half-open, supporting content for which line interpretation would be misleading. Strict decoding matters: replacing invalid characters can produce readable text while breaking the claim that the displayed span corresponds to the original bytes. CRLF content remains byte-exact. A locator therefore records a reproducible reading operation rather than a file name that happens to exist today.

Successful verification establishes that the caller-bound local checkout contains the stated immutable content at the stated revision and path. It does not prove that a mention is an import, that a dependency is executed, or that a remote organization owns the repository. A fork can share identical objects. Detector truth needs a separate check against the bytes, and remote attribution needs an independently trusted repository binding. Keeping these assurances separate prevents a strong byte-level result from inflating an architectural inference.

The verifier disables replacement objects and lazy fetching, ignores ambient repository overrides, and uses bounded local object reads. Source size, tree depth, tree entries, cumulative traversal work, and subprocess duration have limits. Missing objects or unsupported Git capabilities cannot become a successful verification. An unavailable result preserves the distinction between evidence that was contradicted and evidence that could not be checked. This is also a practical design rule: a verifier should finish with an intelligible result when the environment is incomplete.

A small source laboratory that survives inspection

The observatory fixture contains four actual local Git repositories, each with six deterministic commits. Their relationships are synthetic and explicitly disclosed; the objects and verification operations are real. Four public immutable locators are checked, and an actual span-digest mutation is rejected. Exporting the fixture sources preserves the repositories so another process can verify those locators after fixture construction returns. A nonempty output directory is refused before existing work is changed.

Use python -m x3dray fixture-sources --out ./fixture-sources to retain that specimen. Its exported dataset and family configuration map canonical repository identities to the four local source directories. A selected witness can then be checked with python -m x3dray verify-witness --repo ./fixture-sources/evidence --repo-id CANONICAL_ID --locator WITNESS.json, using the actual identity and locator from the export. The command is an offline verification step; it does not authenticate a GitHub account or contact a remote to repair missing objects.

Binding the scene to a bounded source projection

The modern scene contract declares source_binding_schema: 1. Each semantic relation carries the same source digest in its plan record and emitted XML metadata. The independent scene reader recomputes the binding from the supplied source ledger and also reads the actual world geometry. Metadata establishes identity; it cannot override where the XML places a glyph or polyline. A transformed scene can remain equivalent even when its XML representation changes, while a displaced endpoint can fail despite unchanged metadata.

For public records, the binding includes the first four substantive witnesses in source order, with top-level string fields capped at 160 characters. Supported locator objects are normalized and retained structurally, including their full immutable identifiers. The payload also binds endpoints, source type, grade, detector summaries, and the evidence total. The total is clamped to at least the raw evidence-list length; an invalid or undersized declared total cannot conceal supplied records. Projecting an already bounded page record remains idempotent when that total is preserved.

This digest binds the disclosed sample and counts. Changing a fifth witness's text while preserving the sample and count need not change it. Calling it a hash of all underlying evidence would overstate the contract. A complete scene_sources ledger retains source membership even for unwitnessed, self-related, or invalid-grade inputs, allowing the verifier to check explicit omission reasons. Coverage is an invariant across eligible relations and justified omissions, rather than a count of whatever the renderer elected to display. Legacy plans remain inspectable through verify-scene, while the release gate requires the current source-binding contract.

If either endpoint is private, the witness binding uses aggregate counts. Hidden paths, text, locators, and free-form curated kinds cannot influence the digest. Known detector classes retain their counts; unknown private detector names are combined under an aggregate class. Endpoint identities and the declared grade remain part of the disclosed relationship. This policy treats privacy as an information-flow property: substituting hidden content at fixed public aggregates should leave the public projection unchanged. A hidden-content hash would still expose distinctions between private versions.

Two clocks, two questions

observed_by asks which claims had been recorded by an instant. valid_at asks which claims explicitly assert validity at an instant. Validity uses bounded half-open intervals: start <= at < end. Unknown validity remains unknown. Including unknown records is an explicit policy choice, and a path requiring an unknown-validity hop is marked provisional. Calendar validation, timezone normalization, and microsecond precision keep the comparison rules precise across Python and JavaScript.

The four-node counterexample makes the difference concrete. Alpha–beta is valid over January 1–3; beta–gamma is valid over January 3–5. Their intervals touch at January 3 but never overlap, because the first excludes its end. No common query instant establishes that two-hop route. Alpha–delta has a wider known interval, while delta–gamma has unknown validity. Including unknowns can expose that alternative as provisional. By January 5, an observation-time query can return both recorded routes without establishing that either was historically co-valid.

Git author dates do not supply missing validity. A recently harvested old commit tells us something about the observed source history; it does not establish when a relationship became true or ceased to hold. The user interface should keep the active clock, query instant, unknown policy, and omission ledger visible with the result. A technically correct temporal filter is insufficient if the reader cannot tell which question it answered.

The matrix contains 10, 100, and 1,000 generated entities across chain, modular, and branching topologies. Each stage uses seven measured repetitions after two warmups. An independent bounded path enumerator checks returned routes and counts, including incoming traversal, disconnected nodes, and parallel supporting records. Read these results as shared-host diagnostic samples. The median and nearest-rank p95 describe the retained samples; seven observations do not establish a production tail-latency guarantee. Compilation, checking, projection, and query calls are timed separately. Fixture construction, imports, and JSON/IPC are excluded unless the report states otherwise. Source hashes are captured before and after the experiment, and a source change invalidates the run. Reproducibility includes knowing which implementation produced a measurement.

Python allocation measurements use separate tracemalloc calls, avoiding tracing overhead inside the timing samples. They describe traced Python allocations rather than total process memory. Node reports process snapshots without forced garbage collection; a negative heap delta can reflect collection. The optional jsdom experiment constructs and serializes an SVG mirror of the scene plan. It does not measure browser layout, paint, the production workbench, X_ITE rendering, or GPU throughput. Resource refusals at graph and expanded-scene work limits are tested as refusals, not counted as semantic successes.

A measured layout repair, with a precise boundary

The original fixed-ring arrangement produced 7,936 overlapping glyph-bound pairs in the 1,000-entity specimen. Adaptive concentric rings reduced that diagnostic to zero; the closest-pair surface gap changed from −0.56493 to +0.34968 world units. Ring capacity now follows glyph bounds and spacing, and the constellation's extent determines the framing camera. This is a useful architectural repair because it replaces a fixed visual assumption with a geometric invariant that survives a much larger population.

Zero glyph-bound overlaps does not establish legible labels, uncrossed edges, good picking targets, or readable pixels. The measured scale fixtures use spherical glyphs, and the reported gap belongs to the closest-centre pair. Box and anisotropic glyph diagnostics need their own conservative bounds. The static reader checks semantic glyphs, relation polylines, transforms, attachment, source coverage, and grade colours within its declared scope. Labels, decorations, other scene regions, runtime interaction, and rendered appearance remain separate. Each needs its own acceptance criterion before it contributes to a broader usability claim.

The observatory as a creative development surface

The local browser experience combines cached Python audit results with live shared-JavaScript architecture queries. Selecting an XML mutation inspects the independent check performed during the build; the browser does not rerun Python. Changing a query executes the production JavaScript tool. The scale view can display the complete 1,000-entity modular plan and link its actual X3D artifact. Its DOM-update readout excludes paint, while its schematic glyphs communicate plan geometry rather than verified pixel appearance.

This separation supports an engaging interaction grammar: inspect a claim, open its source locator, move the time lens, and compare the surviving path. A mutation gallery can teach why a transformed-but-equivalent scene passes while a forged endpoint fails. The most useful animation would reveal a change in evidence or eligibility, with the exact reason available beside it. Motion should help a reader understand a transition rather than suggest that an uncertain relationship has become certain.

Next priorities and their completion criteria

The next temporal step is a two-axis query: “known by K, claimed valid at V.” Today the two modes answer separate questions. The combined filter should first respect a knowledge cutoff and then test validity at one shared instant, while reporting unknown and excluded records on both axes. Acceptance requires cross-language agreement, exclusive-boundary tests, and counterexamples involving late-arriving historical assertions. Quietly treating valid_at as an implicit knowledge cutoff would change the present meaning and should be refused.

An append-only snapshot and retraction model should follow. Preserve the original assertion, its observation event, and later corrections or retractions as distinct records with explicit relationships. The test is whether an earlier investigation can still replay against its exact source and analysis identities after a correction arrives. Never overwrite a historical claim merely to make the latest view look consistent. Content-addressed snapshots can also become cache keys, provided private hidden content does not enter public identities.

Detector reruns should form the next assurance layer over immutable locators. A detector adapter should consume the located span or blob, declare its version and predicate, and produce a result that can be compared with the recorded assertion. Acceptance requires a detector-changing mutation to fail even when the Git bytes still verify, plus an honest unavailable result for unsupported detectors. A matching path, successful byte digest, or familiar package name must never substitute for rerunning the actual detection rule.

For larger scenes, prioritize semantic detail on demand: a stable glyph overview, labels for the active neighbourhood, and richer evidence when selected. Index repeated queries against immutable graph snapshots and cache source verification by complete content keys, repository binding, verifier version, and policy. Establish invalidation tests before optimizing. Then review a real public repository family for predicate accuracy and misleading omissions, and run browser/GPU measurements separately for frame time, picking, text loading, memory, and interaction latency. Synthetic throughput cannot approve those outcomes.

Validation and practical use

The final source passes 442 Python tests and 23 DOM integration checks. All nine scale scenes pass the independent checker and the Python/shared-JavaScript path-oracle comparisons. Baseline, equivalent-transform and nine scale scenes pass the official X3D 4.0 schema. Four immutable Git file witnesses are rechecked with the installed package; the altered-span probe is rejected. Python and JavaScript replay the same saved time-filter history to an identical state.

The kit includes the offline localhost lab, a dependency-free Python wheel, actual scale specimens, raw measurement samples, local synthetic Git bundles, validation scripts and both incremental and cumulative patches. A small scale run and its observatory export were also executed from the installed wheel, outside the checkout.

Real browser layout, text readability, X_ITE pixels, GPU memory and frame rate remain unverified here. The DOM scene-reuse check uses a renderer stand-in. A full real-family eight-gate release run still needs its own environment. No upstream push was made.
