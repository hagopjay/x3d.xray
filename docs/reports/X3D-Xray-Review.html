A technical and creative teardown, with an executable next step. Reviewed November 12, 2026. Source snapshot: b3fec1f7307a08a830bb82cf7693fad9537965ae.

The most valuable thing in this repository is its approach to knowledge: witnessed relationships, declared exclusions, inspectable computation, and a visual distinction between counted facts and interpretation. That is a compelling basis for an evidence observatory for the X3D ecosystem. Its next major advance should be making these promises enforceable across ingestion, publication and interaction, then extending the kinds of architecture it can reveal.

My recommendation is to develop three tightly connected capabilities: trustworthy snapshots, typed architectural relationships, and replayable investigations. Keep the lightweight Python analytical kernel and X3D scene. Extract the contracts already implicit in the code before adding another framework or service.

2. What is unusually good — preserve it

The evidence has a vocabulary. “Unknown is not zero,” “no recorded session link,” and “no witness, no tie” are useful analytical constraints. Many dashboards obscure the distinction between absence, exclusion and unmeasured data; this repository has already made that distinction central.

The agent and the human use the same tools. web/tools.js serves both the page and MCP. This is a good foundation for parity tests and reproducible investigations. Preserve one implementation of analytical operations as transport adapters multiply.

The mathematics has independent tests. The FCA tests compare concepts against their mathematical definition. Centrality tests compare results against brute-force small-graph oracles, including weighted graphs. Rational distances avoid treating genuine path ties as unequal because of floating-point noise. This is substantially better evidence than snapshots of whichever answer the implementation happens to return.

The analyzer considers its observer effect. ties.py:110 sets aside the observer repository's incidental mentions rather than discovering dependencies created by its own configuration and documentation. Extend this into an explicit detector policy.

The presentation has a coherent visual grammar. Helix, constellation, city, lattice, bridges and pipeline are complementary views of the same history. Boxes versus merge spheres, author colours, heat roofs and fog are meaningful encodings. Retain their analytical meaning as visual richness grows.

The system can explain its own construction. Source hashes, definitions, stage descriptions and signal code give how_built real substance. The next step is binding those explanations to the exact immutable build being viewed.

3. The current architecture and its real boundary

The pipeline is a small in-process build system: Git/configuration → dataset and ties → concepts/bridges → profile → narrative slots/self-description → scene/layout → web bundle → gates → receipt. The web page and MCP server then read the same exported data. This is a sensible topology for the present scale.

There are two different products inside it:

Reusable core Family-specific exhibition
Git ingestion, identity mapping, FCA, centrality, exclusions, evidence records, tools Named repositories, focal hub, lineage arrangement, author labels, cameras, example questions and some gate fixtures

The distinction is currently implicit. compiler.py:608 enumerates particular repositories for constellation rings; lines 619–620 always create x3d_mcp and upstream nodes. A new arbitrary configured repository can appear in the city without entering the constellation. Several frontend self-tests also assume this exact family.

Make the exhibition a theme. A FamilyTheme should contain display names, colours, aliases, focal roles, layout anchors, optional external entities and preferred viewpoints. All unanchored dataset entities should still receive deterministic placement. Preserve the current handcrafted composition as the HagopJay theme; add a tiny alpha/beta fixture to prove the core's portability.

Do this gradually. Extract one region builder at a time from the roughly thousand-line compiler. Introduce a renderer-neutral scene plan before considering a renderer replacement. No microservice or distributed graph database is justified by the evidence collected here.

Explicit registered-output manifest; one file set for scanning, hashing and publishing; clean staging and final promotion.

The publication gap is one architectural problem, not three unrelated bugs

page.py:259 discovers publishable files by walking the output directory. gates.py:33 defines a smaller static set to scan. receipt.py:51 hashes a fixed set of generated outputs plus vendor trees. These are three definitions of a release.

The controlled reproduction placed only synthetic canaries in an extra JSON file. That file entered the publication map, privacy returned pass, the receipt omitted it, and mutating it did not change the receipt digest. The appropriate fix is a single registered set of released bytes. Merely adding another filename to a scanner leaves the underlying mismatch.

Use a fresh staging directory for each build. Register each emitted asset with path, role, content type and source stage. Refuse unexpected files and escaping paths. Validate and scan the registered set, including the reports produced by gates. Hash the final asset bytes into a detached receipt. Exclude the receipt's own hash explicitly; self-hashing cannot be solved by including itself. Verify a sealed manifest and promote the staging directory only when the release policy passes. Keep the manifest independent of absolute machine paths for portable content identity.

The companion release_audit.py demonstrates a narrow independent boundary: reviewed asset allowlist, path/source consistency, mandatory gates, owned-text canaries and receipt byte coverage. It remains read-only and supplements the existing gates. Its regex checks are a limited detector, not a proof that all sensitive information has been removed. Trusted vendor assets must be explicitly pinned and reviewed rather than silently exempting any folder named “vendor.”

Fact integrity has several different meanings

The slot system is useful, but slot resolution does not establish the truth of a sentence. A synthetic claim saying “All {family_span.commits} commits are defect free” renders as “All 2 commits are defect free” with no reported problems, although the signal counts commits and says nothing about defects. spec.py:153 validates references, basis and the presence of a slot, not entailment.

Separately, gate_fact():78 trusts saved rendering problems instead of recalculating from the raw spec/current profile. A stale or edited rendered object can therefore pass. The declared JSON schema is also not applied: render_spec({}) accepts a structurally empty spec without reporting required-field errors.

Report four scopes independently: shape validity, numeric/reference validity, evidence relationship, and human interpretation. Use deterministic claim forms for claims that can be verified exactly: comparisons, counts, extrema, scope and denominators. Keep free prose as interpretation, with evidence links and review status. An LLM may critique an interpretation, but its endorsement should not become a deterministic fact verdict.

Witness checks need an independent representation

gates.py:192 checks the layout's records rather than reading scene semantics. A passing XSD gate can establish syntax/type conformance; it cannot establish that a line connects the repositories asserted in the bundle. A missing XSD dependency can also be skipped under today's aggregate rule.

Attach stable entity/evidence IDs to scene objects through appropriate X3D metadata and a scene plan. Independently parse the emitted X3D, then check entity existence, type, edge endpoints, grade, ID uniqueness and bundle correspondence. Mutate the actual scene in tests while retaining a valid layout: injected edge, wrong endpoint, removed node, altered grade, absent scene. This verifies the rendered artifact rather than two copies of its intended metadata.

5. Ingestion: the most important source of quiet errors

The filename reproduction is an instructive failure: git log --numstat quotes some paths, while ls-tree -z supplies actual paths. gitio.py:58 parses line/tab-separated display text. The harvester then joins different keys. Later FCA, graphs, profile and gates can all agree perfectly with the same inaccurate dataset. Agreement downstream is weaker than fidelity at the source.

Implement byte-safe NUL-delimited parsing for the documented Git record format, including metadata delimiters and filename boundaries. Handle Unicode, tabs, newlines, quotes and backslashes; choose an explicit reversible policy for non-UTF-8 paths. Do not fix this only with core.quotePath=false: control characters and arbitrary Git path bytes still need a real parser.

Create a RepositorySnapshot with exact ref→OID map, selected default ref, shallow status, object format, upstream availability, effective author/history filters, author-versus-committer clock and read outcomes. %at currently supplies author time, while some prose describes when commits “landed.” Store both clocks and name the selected one. Missing upstream history should be partial knowledge, not an implicit change in the definition of the family's identities.

Use typed outcomes for blob reads: measured text, binary, too large, unavailable, failed. gitio.py:109 currently turns a failed blob read into empty bytes. Line totals also combine measured values with unmeasured large/media files as if the latter contributed zero. Attach coverage denominators to line totals: measured files/bytes, skipped categories and failures.

Pin the ref set before the harvest, or reject/retry a changed snapshot. Avoid a tree measured after history has moved to a different revision. For performance, stream history instead of capturing the complete log string and use a persistent git cat-file --batch process plus blob-OID caching rather than one subprocess per file.

Keep these as modules and typed records in one package. Start with schema versions and validation at stage boundaries. A stage record should contain input content digests, algorithm/parameter version, output digest and verification scopes. Refuse stale optional artifacts whose parent digest differs; skipping curated must not silently reuse a previous curated.json merely because it exists.

Separate two identities: a content identity over normalized source snapshots, configuration, parameters, code/dependencies, narrative, theme and assets; an execution record containing timestamps, elapsed timings, platform and actual gate runs. The existing receipt mixes changing run data into its digest. That is useful run traceability but should not be advertised as identical semantic content producing an identical digest across runs.

An evidence example, deliberately schematic:

Full object IDs stay internal; display abbreviation is a separate concern. Hashes of known names or session identifiers are pseudonymous identifiers, not an automatic guarantee of anonymity. Enforce disclosure choices through publication policy, not through assumptions about hash opacity.

7. Give the graphs richer semantics

The current constellation combines several kinds of connection: imports, manifest mentions, CI use, shared files, sessions, forks and asserted lineage. They answer different questions. tools.js:417 explicitly walks ties in both directions while also recommending the tool for dependency questions. A documentation mention or session path cannot establish a directed executable dependency.

Relation Direction What it supports
imports, declares_dependency, uses_validator Directed Recorded code/build use under a named extraction method
pins_revision Directed A source artifact identifies an exact validated target revision
shares_blob Symmetric Identical content; by itself no proof of origin or execution
participated_in_session Entity→session membership Recorded session overlap; no automatic dataflow claim
fork_of Directed Recorded repository ancestry
claims_lineage_from Directed, attributed The owner's account of conceptual lineage
mentions Directed Lexical association under a detector rule

Add traversal filters for predicate, direction, evidence grade, snapshot and maximum hops. Surface relation types along each path. Preserve the existing association graph as its own useful lens. Do not convert C/L/S categories into numerical probabilities or multiply grades into a path confidence without a calibrated model.

Deconfound analytical lenses. The current count-versus-Jaccard comparison changes both the distance and whether high-churn files are removed. Add a small factorial comparison: count/all, count/pruned, Jaccard/all, Jaccard/pruned. This tells the viewer whether a bridge changed because of weighting or removal.

Show threshold sensitivity. With the current cutoff, a 15-file commit contributes 105 co-change pairs while a 16-file commit contributes none. Compare thresholds such as 5/15/30 and a separately named per-commit-normalized variant. Record the exact inclusion policy and exceptions; robustness across reasonable settings is often more useful than a single dramatic ranking.

Keep authorship honest. Commit count, changed lines, trailers and recorded sessions describe metadata and different denominators. They do not measure code quality, effort, authorship certainty or creative contribution. Present them as recorded attribution.

Expand FCA by adding separate contexts. Five author-class attributes allow at most 32 possible intents, so the current author lattices do not need a heavyweight FCA rewrite. The exciting expansion is files × X3D constructs, modules × validation responsibilities, repositories × interoperability surfaces, and files × capabilities. Derive each attribute from inspectable parser/schema/AST evidence. Introduce concept limits and pruning as these larger attribute spaces become real.

8. Performance: measured pressure points and a disciplined path

The strongest measured bottleneck was not the renderer. _bipartite() computes passage points for each connected repository pair, and each passage-point query removes vertices and recomputes connectivity. The approximate cost is O(R²·V·(V+E)); sparse chain growth with R proportional to V approaches quartic work.

Synthetic sessions Repositories Nodes Observed _bipartite() wall time
10 11 21 0.0087 s
20 21 41 0.1124 s
40 41 81 1.4118 s
60 61 121 7.0553 s

These are single local observations on synthetic chains. They isolate one routine, not full builds. A block-cut forest can index articulation structure once; obligatory passage nodes then lie on its path between repository vertices. Compare against today's implementation on generated small graphs before changing production. Outputting all repository pairs remains quadratic even after computation improves; support pair-specific queries and pagination.

For weighted betweenness, process independent components and cache by graph content/parameters. Keep exact reference computation for small graphs. If sampling is added later, label approximate values with sampling scope and uncertainty, never as a silent fallback. The production verifier currently checks substantial witness/topology/internal consistency, while exact weighted magnitudes are oracle-tested in the test suite; report that scope accurately rather than describing every magnitude as independently proved per build.

Browser and GPU work

app.js:400 visits every commit and resolves named scene nodes during recolour/highlight. Cache handles once, cache repository colour indices and update the symmetric difference for highlight transitions. Batch larger changes over frames when profiling establishes long tasks. Picking currently scans candidates and the city uses roof-centre proximity; geometry-to-entity mapping or bounding volumes would improve both accuracy and scale.

The compiler already batches city boxes into shared meshes: preserve that useful optimization. Commit glyphs still have individual transforms/materials. Benchmark aggregation and focused overlays before adopting renderer-specific instancing. Maintain a stable semantic ID→render primitive mapping so performance work does not destroy picking and evidence links.

X_ITE documents LOD distance-based representation selection. Use repository/district summaries at overview distance, clustered records at medium distance and exact selectable entities when close. LOD is not automatic network streaming: representations still need explicit loading, eviction and event management if those become necessary. StaticGroup can enable optimization for truly static subtrees, but its documented event/immutability constraints make it inappropriate for materials the highlight code mutates. When using it with the current Immersive profile, declare the required Grouping component support. Verify all proposals against the pinned runtime and X3D 4.0 validation target.

The current live gate launches SwiftShader. A pass there would be valuable functional evidence, not a measurement of the user's GPU. Maintain a separate hardware benchmark record with renderer, driver, viewport, DPR, dataset digest and scene settings.

Measure Instrumentation Initial proposed budget, not measured performance
Harvest/build stages perf_counter, cProfile, tracemalloc, subprocess counts, bytes Detect regressions on fixed 1k/10k/100k synthetic-commit fixtures
Scene boot fetch, parse, browser-ready and first-useful-view marks Set a target such as 3 s on a named desktop reference fixture

Keep “more GPU usage” subordinate to faster and clearer interaction. CPU-bound Python graph work does not become GPU work by replacing X_ITE or enabling a different browser backend. A GPU analytics experiment should follow evidence that algorithmic and data-layout fixes are insufficient.

9. Creative directions that make this a distinctive instrument

A. Evidence microscope — highest immediate value

Select a bridge, and its actual commit witnesses light up in the helix, participating files appear in the city, and a synchronized drawer shows source snapshot, detector, exclusions and alternative metrics. “Why does this exist?” becomes one coherent interaction. Keep counts and evidence available when the scene cannot load, and give keyboard users the same selection model.

Success criterion: a reviewer can trace a displayed architectural statement to the exact source observation in two deliberate actions, without an AI response being required.

B. Chronoscope — compare how architecture changes

Compare two immutable snapshots: new dependencies, missing witnesses, changed pins, bridge-role changes and capability additions. Preserve layout anchors between versions so motion has meaning. Use before/after evidence panels; a line changing does not establish what caused the change.

Success criterion: every highlighted delta has a stable entity ID and inspectable before/after source record. Repo/path continuity should be explicit, with rename evidence rather than guessed identity.

C. Capability cathedral — the most X3D-specific extension

Replace the single “who touched it” question with a parallel lattice of interoperability capabilities: X3D validation, scene parsing, geometry conversion, Gaussian-splat handling, material support, animation, provenance and bridge IO. Light the repositories that implement each combination. Drill into the actual constructs or code paths behind the attribute.

Begin with a small capability vocabulary and a fixture whose answers are known. Separate “declared in README,” “implemented in parsed code,” “exercised in tests,” and “verified in a runtime result.” That progression can reveal integration opportunities between your repositories without turning attractive labels into unsupported claims.

Success criterion: the tool produces a short evidence-backed integration shortlist, each with a shared interface, a missing interface and a smallest executable experiment.

D. Bottleneck laboratory — graph counterfactuals

Temporarily remove a selected file or recorded session and show graph fragmentation, alternative paths and affected clusters. Label the result as a graph experiment. A co-change cut vertex is not automatically a module whose deletion crashes the product; the display should preserve that distinction.

Pair this with a sensitivity panel showing which bottlenecks survive alternate thresholds and weightings. Stable discoveries deserve attention before unstable high scores.

E. Replayable investigation theatre

Serialize the existing camera, highlight, colour and note operations into a storyboard tied to a build digest. Each beat contains the query, result/evidence IDs, selection state and narration. An agent can propose a tour; deterministic validation resolves its references; the viewer can pause, inspect and replay it.

Treat notes as structured annotations rather than transient text: entity ID, snapshot/build identity, evidence IDs, author and text. A note attached to an old snapshot should visibly remain an old-snapshot note.

F. Freshness and uncertainty weather

Give different unknown states different encodings: unmeasured history, withheld private detail, stale curated evidence, mass-edit exclusion and missing trailers. Keep the baseline solid; show stale or uncertain information with restrained patterns, opacity and explicit text. Avoid using fog for every form of uncertainty, which would make distinct causes indistinguishable.

G. Change-review rehearsal

Feed a proposed change or branch comparison into a review workspace. Ask: Which validated contracts are touched? Which bridge surfaces changed? Which tests exercise them? Which evidence needs refresh? Start with read-only branch/snapshot comparison. Proposed source edits remain a separate operation with their own tests and review.

H. An accessible analytical twin

Offer a keyboard-operable entity table, a 2D relation view and the 3D environment over one selection/filter state. Exact comparisons belong in sortable tables; spatial views support orientation, pattern finding and exploration. Add reduced motion, colour-independent relation cues and explicit visible/total counts. The current city shows at most 64 files per repository; label that sample and make omitted records queryable.

12. Companion kit and how to use it

The ZIP contains this report, source-linked findings, the synthetic evidence scripts/results, an architecture contract example and an independent release-audit scaffold. It contains no cloned family repositories or harvested user data.

  1. Run the existing repository tests from its checkout: python3 -m unittest discover -s tests -v.
  2. From the kit, run python3 evidence/pipeline/reproduce_pipeline.py /absolute/path/to/x3d.xray, python3 evidence/runtime/reproduce_runtime.py /absolute/path/to/x3d.xray, python3 evidence/core/core_probe.py --repo /absolute/path/to/x3d.xray, and python3 evidence/check_claims_receipts.py /absolute/path/to/x3d.xray. Read each script's header; the core probe includes the synthetic scaling run. Diagnostic success means a probe ran, not that the current code is release-ready.
  3. Test the separate scaffold: python3 -m unittest discover -s scaffold -v.
  4. Adapt scaffold/release.allowlist.example.json to the exact reviewed dependency/assets set. It is intentionally incomplete and labelled as an example; do not approve every file simply by enumerating an existing output folder.
  5. Run python3 scaffold/release_audit.py --site /absolute/path/to/out --allowlist reviewed-allowlist.json. It returns nonzero for a boundary failure. Current generated builds may correctly fail until release policy and asset attestation are repaired.

The scaffold verifies ordinary output byte hashes and the repository's current aggregate vendor-tree hashes. It does not authenticate a publisher, validate arbitrary secrets, reconstruct narrative truth or replace the existing analytical gates. A signed receipt could be a future addition when provenance across parties matters; it is not needed to fix today's manifest mismatch.

13. Heuristics to carry into every iteration

  • Keep observations, interpretations and interventions separate. A counted event, a narrative about it and a simulated graph deletion have different meanings.
  • Never let display limits alter analytical truth. Grade/count first; sample/paginate second; report omissions last.
  • Make every important visual answer a source question. “What does this mean?” should lead to a predicate, denominator, snapshot and witness.
  • Use full identities internally and short labels at the surface. Abbreviation should never weaken pin validation.
  • One release has one definition of its bytes. Scanner, manifest and receipt should consume the same registered asset set.
  • Keep independent oracles small and honest. Use them to validate optimized algorithms, then record precisely which production values were independently checked.
  • Optimize the measured bottleneck. On this review's synthetic graph, CPU connectivity work is the clear early pressure point; no GPU speed claim was measured.
  • Preserve layout continuity across snapshots. Spatial motion should communicate a data change rather than an arbitrary re-layout.
  • Be explicit about samples. “64 shown / N files” communicates more than a district that looks complete.
  • Extract contracts before replacing frameworks. The existing code has good primitives; naming their boundaries is the shortest route to a stronger product.
